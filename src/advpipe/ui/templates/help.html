How advpipe works

advpipe takes one task, a work item, and has a team of AI agents build it on a new git branch. Every piece of work is checked by a second agent whose only job is to find what's wrong with it, and by your project's own tests and checks. When it's done, the branch waits for you: advpipe never merges or pushes.

The steps

Every run goes through the same steps, in this order. The program running them is ordinary code, not an agent, so no step is ever skipped.

  1. SPEC. The spec writer turns your work item into task.md: what to build, as numbered acceptance criteria (AC1, AC2, ...), plus anything unclear as open questions. A question marked BLOCKING stops the run here, for you to answer.
  2. TESTS. The test author writes tests for the criteria, before any code exists, and the tests must fail (there's nothing to pass yet). The test critic looks for gaps. Up to {{ limits.max_rounds_tests }} rounds by default.
  3. CODE. The coder changes the code until the tests and checks pass, without touching the tests. The code critic looks for bugs and unmet criteria. Up to {{ limits.max_rounds_code }} rounds by default.
  4. REVIEW. A standards reviewer and a security reviewer each read the whole change once, at the same time. There's no back-and-forth with them: anything they say must be fixed goes to the arbiter.
  5. ARBITER. Only if must-fix findings are still open after a step (after its last round, or from the reviewers). The arbiter decides, for each, fix or dismiss, with a reason; a failed check is always fix. If anything is to be fixed, the author gets one more pass and the checks run again. Usually it isn't needed.
  6. FINAL CHECKS. All checks run once more on the finished branch. Green means the run is complete.

A round is one try by the author, followed by the checks and the critic's verdict. If the critic says PASS, the step is done. If not, the author gets the findings and tries again, up to the round limit. What's still open then goes to the arbiter.

The agents

Each agent has one job and its own instructions (its role prompt: see a run's Spec & context tab). Only one agent changes files at a time. Critics and reviewers only read: they return findings, never edits. And they judge the work itself (the spec, the diff and the check output), never the author's explanation of it.

Checks

Checks are your project's own commands, run by advpipe itself, not by an agent. Their result is facts, not opinion: a check that fails always counts as a problem that must be fixed, whatever a critic says. (In the config file and on the command line they're called gates.)

A finding is one problem a critic or reviewer reports. It must point at a file and line, or at an acceptance criterion. Blocking findings must be fixed (or dismissed by the arbiter) before the run can finish; minor ones are noted in the report.

Using this UI

  • Runs lists every run in this repo, newest first, and updates itself. Click a run for its page: status and cost, the live log, the timeline with every round (what the author replied, the check results, the diff the critic judged, its findings), the report, and the commands to run next.
  • Work items are markdown files describing one task each, kept in your repo. Write and edit them here, then Run one. Saving writes the file; committing it is up to you.
  • New run shows the branch it will make, the config it uses and how much it can spend, before anything starts. Runs carry on in the background, even if you close this page or stop the UI.
  • A run's buttons (Cancel, Resume, Clean up) only show when they make sense. Each one does exactly what the same advpipe command does in a terminal.
  • Everything here can also be done from a terminal: advpipe --help lists the commands. Runs started there show up here too.
  • Theme: the button at the top right switches between your system's setting, light and dark. Everything can be used with the keyboard: Tab moves between links and buttons, and Enter opens a step or round.

Money and safety

  • Every run has a budget ({{ "$%.2f" | format(limits.budget_usd_per_task) }} by default). It stops when it's spent, and you can resume it with a bigger one. The New run dialog says how much a run can spend before you start it.
  • Agents work in a separate copy of your repo (a git worktree), on their own branch. Your working copy and branches aren't touched.
  • Nothing is merged or pushed. Merging is your decision; the run page gives you the commands to copy.
  • This UI is for this computer only. It listens on 127.0.0.1 and needs the link with the token that advpipe ui printed. Don't share that link: anyone with it could start runs, which spend money and run commands.

Words used here

work item
The task you give advpipe, in a few lines of plain text.
task.md
The spec the spec writer makes from it. Every later agent works from this, not from the work item.
acceptance criteria
The numbered, testable statements in task.md that say when the work is done.
author / critic
The agent that does a step's work, and the one that checks it.
finding
One problem a critic or reviewer reports: blocking or minor.
round
One try by the author, then the checks and the critic's verdict.
checks (gates)
Your project's tests, type checker, linter and security scanner, run by advpipe.
run id
The name of a run's folder, .advpipe/runs/<run id>/, which holds everything it did.
